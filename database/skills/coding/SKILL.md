# Coding Skill — Arona Discord Context

This skill applies whenever Sensei asks for code. Arona runs code in a sandboxed Docker environment via `run_code`. Text files (HTML, JSX, scripts, configs) are delivered via `create_files` + `send_files`. Binary outputs (images, charts, PDFs) are generated by `run_code` with `send_output=true`.

## Delivery Model

| Output type | Tool | Notes |
|-------------|------|-------|
| **Text/code file to send** (html, jsx, py, json, md…) | `create_files` → `send_files` | Preview link auto-appended for html/jsx/md |
| **Edit text/code file sent in previous message** | `edit_file` → `send_files` | Edits are appended as new file versions, not replacing old ones |
| **Binary file** (image, chart, PDF, docx…) | `run_code(send_output=true)` | Write to `OUTPUT_DIR` env var |
| **Inline code snippet** (shown in message) | Fenced code block | Backend auto-converts to file if too long |
| **Executing code** (runs + produces output) | `run_code` | Use `action="run_code"` or `action="run_shell"` |

**Never use `run_code` just to write a text file to disk or edit a text file. Use `create_files` and `edit_file` instead.**

## Core Philosophy

Write code as if a senior engineer will review it tomorrow. Every line should be intentional. Cleverness for its own sake is a bug, not a feature.

Before writing a single line:
- Understand what the user actually needs, not just what they literally asked for
- Identify edge cases upfront
- Choose the simplest approach that correctly solves the problem
- If multiple approaches exist, briefly explain the trade-offs before committing

## Universal Rules (All Languages)

### Naming
- Variables, functions, and classes must be named for what they ARE or DO, not how they work internally
- Avoid: `data`, `temp`, `val`, `x`, `obj`, `result` (except in truly trivial throwaway contexts)
- Boolean variables: use `is`, `has`, `can`, `should` prefix — `isLoading`, `hasError`, `canSubmit`
- Functions: use verb + noun — `fetchUser()`, `validateEmail()`, `parseCSV()`

### Functions
- One function = one job. If you need "and" to describe what a function does, split it.
- Keep functions under ~30 lines as a rule of thumb. Longer usually means it should be decomposed.
- Pure functions (no side effects) wherever possible. Side effects should be explicit and isolated.
- Parameters: if a function takes more than 3-4 params, use an options object/dict instead.

### Comments
- Comment WHY, not WHAT. The code shows what; the comment explains reasoning that isn't obvious.
- Bad: `i += 1  # increment i`
- Good: `# Skip the header row which doesn't contain data`
- Remove commented-out dead code before finalizing. Use version history for that.

### Error Handling
- Never silently swallow errors. At minimum, log them.
- Fail loudly and early. Defensive programming is not the same as hiding failures.
- Give users/callers actionable error messages, not internal error codes.
- Always handle the unhappy path — null, empty, network failure, invalid input.

### Constants
- Never hardcode magic numbers or strings inline. Name them.
- Bad: `if (status === 3)`
- Good: `const STATUS_COMPLETED = 3; if (status === STATUS_COMPLETED)`

## JavaScript / TypeScript

### General
- Use `const` by default. `let` only when reassignment is genuinely needed. Never `var`.
- Use optional chaining `?.` and nullish coalescing `??` instead of verbose null checks.
- Prefer `async/await` over raw `.then()` chains for readability.
- Always `await` inside `try/catch` — never let async errors go unhandled.

### DOM & Canvas (HTML output)
- Use `addEventListener` not inline `onclick` attributes in HTML.
- Batch DOM reads before writes to avoid layout thrashing.
- Use `requestAnimationFrame` for animations, not `setInterval`.
- Clean up event listeners and intervals when components unmount or are destroyed.
- Never use `innerHTML` with user-supplied content — XSS risk. Use `textContent` or DOM methods.

### Functions & Structure
```javascript
// Prefer this:
const fetchUser = async (userId) => {
  try {
    const res = await fetch(`/api/users/${userId}`);
    if (!res.ok) throw new Error(`HTTP error: ${res.status}`);
    return await res.json();
  } catch (err) {
    console.error('fetchUser failed:', err);
    throw err; // re-throw so callers can handle
  }
};

// Not this:
function getUser(id) {
  fetch('/api/users/' + id).then(r => r.json()).then(d => { return d })
}
```

### Arrays & Data
- Use `map`, `filter`, `reduce` over imperative `for` loops for data transformations.
- Use destructuring for clarity: `const { name, age } = user` over `user.name`, `user.age` everywhere.
- Spread carefully with large arrays — creates new copies, can be expensive.

## Python

### General
- Follow PEP 8. Use 4-space indentation, snake_case for variables/functions, PascalCase for classes.
- Use f-strings for string formatting: `f"Hello {name}"` not `"Hello " + name` or `.format()`.
- Use type hints for function signatures, especially non-trivial ones.
- Use `with` for file and resource handling — never forget to close files.

### Structure
```python
# Preferred function style
def calculate_discount(price: float, discount_pct: float) -> float:
    """
    Returns discounted price. discount_pct should be 0-100.
    Raises ValueError if inputs are invalid.
    """
    if price < 0 or not (0 <= discount_pct <= 100):
        raise ValueError(f"Invalid inputs: price={price}, discount={discount_pct}")
    return price * (1 - discount_pct / 100)
```

### Pythonic Patterns
- Use list comprehensions for simple transforms: `[x*2 for x in nums if x > 0]`
- Use `enumerate()` instead of `range(len(x))` when you need both index and value
- Use `zip()` to iterate multiple lists in parallel
- Use `defaultdict`, `Counter`, `namedtuple` from `collections` when appropriate — don't reinvent them
- Use `dataclasses` or `TypedDict` for structured data over raw dicts

### Error Handling
```python
# Be specific with exceptions — never bare except:
try:
    result = risky_operation()
except FileNotFoundError:
    logger.error("Config file missing")
    raise
except ValueError as e:
    logger.warning(f"Bad input: {e}")
    return None
# Never: except: pass
```

## HTML / CSS

### HTML
- Semantic HTML first: use `<nav>`, `<main>`, `<article>`, `<section>`, `<header>`, `<footer>` correctly.
- Every `<img>` must have a descriptive `alt` attribute.
- Forms: always associate `<label>` with inputs via `for`/`id`. Use correct `type` attributes on inputs.
- Don't use `<div>` or `<span>` when a semantic element fits better.
- Keep structure (HTML), style (CSS), and behavior (JS) separated as much as possible.

### CSS
- Use CSS custom properties (variables) for colors, spacing, font sizes:
  ```css
  :root {
    --color-primary: #2563eb;
    --spacing-md: 1rem;
    --font-size-lg: 1.25rem;
  }
  ```
- Mobile-first: write base styles for mobile, use `min-width` media queries to scale up.
- Avoid `!important` except as a last resort — it signals a specificity problem.
- Prefer `gap` over margin hacks in flex/grid layouts.
- Use `transform` and `opacity` for animations — they don't trigger layout reflow.
- Name classes for purpose, not appearance: `.card--featured` not `.card--blue`.

## React (for Canvas)

- Use functional components with hooks only — no class components.
- Keep components small and focused. If a component needs to scroll to see, it's too big.
- Lift state up only as far as necessary. Don't put everything in a root store.
- Use `useMemo` and `useCallback` only when profiling shows a real perf problem — premature optimization.
- Keys in lists must be stable and unique — never use array index as key if list can reorder.
- Default export for the main component. Named exports for utilities.

```jsx
// Good component structure
import { useState, useEffect } from "react";

const DEFAULT_COUNT = 0;

export default function Counter({ initialCount = DEFAULT_COUNT }) {
  const [count, setCount] = useState(initialCount);

  const increment = () => setCount(prev => prev + 1);
  const decrement = () => setCount(prev => prev - 1);

  return (
    <div className="counter">
      <button onClick={decrement}>-</button>
      <span>{count}</span>
      <button onClick={increment}>+</button>
    </div>
  );
}
```

## Debugging Mindset

When something doesn't work:
1. Read the error message fully before guessing. Most errors tell you exactly what's wrong.
2. Isolate the problem — smallest possible reproduction.
3. Verify your assumptions with `console.log` / `print` at key points.
4. Check: are you solving the right problem? Is the bug where you think it is?
5. Rubber duck: explain the code aloud, line by line. The bug usually appears.

When reviewing your own code before submitting:
- Does it handle null/undefined/empty inputs?
- Does it handle the maximum/minimum expected values?
- Does it fail gracefully with useful error messages?
- Would someone unfamiliar understand this in 6 months?

## Code in Arona's Sandbox — Specific Notes

Arona executes code in a Docker sandbox via `run_code`. Key behaviors:

- **`OUTPUT_DIR`** env var is set automatically per message (`workdir/<msg_id>/outputs`). Any file written there with `send_output=true` is sent to Discord automatically.
- **Pre-installed libraries**: `pandas`, `numpy`, `scipy`, `sympy`, `matplotlib`, `pillow`, `python-docx`, `pypdf`, `reportlab`, `python-pptx`, `openpyxl`, `xlsxwriter`, `imageio`, `requests`, `aiohttp`, `cryptography`.
- **For HTML/CSS/JS** that needs to be sent as a file: use `create_files` → `send_files`. Everything must be in a single self-contained file. No external dependencies unless from a reliable CDN (cdnjs.cloudflare.com, fonts.googleapis.com).
- **For Python execution**: write to `OUTPUT_DIR` for file outputs. Assume a clean environment — list all imports at the top.
- **Make interactivity obvious** — if the user can click/interact with an HTML page, add clear visual affordances.
- **Include visible output** — code that runs silently is confusing. Add `print()` or chart/file outputs.
- **Test mentally before sending** — code sent to Discord should work first try. No iteration loop available without another `run_code` call.
- **For demos and visualizations**: prioritize clarity of output over performance optimization.
